# Group 4 verdict: surviving and NoCoverage mutants

Method: read each mutant against the source. Where a call was not obvious I applied the mutant to a scratch copy of the tree (/tmp/triage-group4/tree, outside the worktree) and ran the covering spec, or a throwaway probe spec, against it. Those cases are marked **(verified)**.

A recurring point: `IrcClient.handleMessage` wraps every handler in try/catch (client.ts ~2516). Several mutants that make a handler throw on input the original returns early on are therefore equivalent from outside: nothing is pushed and nothing is dispatched. The only trace is a `console.error`.

## Possible bugs

- **client/js/irc/commands/kick.ts:22** — `/kick bob` (two spaces: `rest.split(" ")` gives `["", "bob"]`) → no KICK is sent and nothing is shown. A bare `/kick` is also silent, while `/join` and `/ignore` print a usage error. A typed command that silently does nothing (CLAUDE.md memory: "buttons do what they say"). The mutant is not more correct (it would send an empty nick). The fix is to drop empty args, or to show a usage line. Low severity.

No other mutant in this group points at wrong original code. The "check that can never fire" cases (numerics.ts:198 `!spec`, markread.ts:261 `!chan.readMarker`) are defensive guards, not bugs.

## Weak tests

- **test/irc/handlers/markread.ts — "holds a marker that comes due before 001"**: the debounce fires after the CAP ACK, so the BackgroundQueue's `ready()` gate makes the `!client.isWelcomed` guard redundant. It misses the window between the socket opening and the CAP ACK, where `markReadEnabled` is false and the guardless code drops the marker. (verified with a probe)
- **test/irc/catchup.ts — "lets a channel's marker jump the catch-up once per MARKREAD_JUMP_GAP_MS"**: it waits a full gap after the too-soon marker, so it cannot catch the gap timer restarting on every marker. A steady stream of lines less than 10 s apart would then never jump again (mutant 4955).
- **test/irc/handlers/markread.ts — "markReadAt (a notification's Mark read) sends nothing for a time already marked"**: only a strictly older time is tested. A time equal to the held marker is resent under `<` (mutant 4994).
- **test/irc/commands.ts — "dispatchInput with draft/multiline a /lua snippet over several lines is one snippet"**: it asserts only that no PRIVMSG `return x` went out. It never checks that the snippet ran at all, let alone as one piece; usage-error and no-eval mutants pass.
- **test/irc/closedQueries.ts — "keeps the newest events within the byte limit"**: its input is already newest first, so removing the sort in `encodeClosed` goes unnoticed.
- **test/irc/closedQueries.ts — "skips malformed items"**: no item has junk before a valid value (e.g. `bob:<t>++1`). Dropping the regex's `^` goes unnoticed, because its one leading-junk case (`z:+1`) fails on NaN anyway.
- **test/irc/handlers/numerics.ts — "other errors carries only the fields its parameters fill"**: no case has a spec whose nick or command slot is present but empty (bare `401 alice`, `421 alice`). `&&`→`||` would add `nick`/`command: undefined`.
