# Verdict: v1 is a useful replay seed, not a client-conformance result

Static review only; no TLC or generator run. The supplied summary attributes all 57 expected outcomes to module/config/property, including the new regressions. It does not contain counterexample steps. Accept the reported cluster results, but do not mistake them for replayable causal traces (`model/results-h1.summary:1`, `model/results-h1.summary:57`, `HISTORY-REVIEW-3.md:23`).

## 1. Review-3 disposition

- **v1 proceed items implemented:** empty JOIN initialization avoids `time[0]`; reconnect, JOIN and more have distinct initial selectors and obligations; FAIL is a separate reply and stop. JOIN/more deliberately share the one-page stop, not reconnect's floor loop (`HISTORY-REVIEW-3.md:21`; `model/History.tla:91`, `model/History.tla:106`, `model/History.tla:158`, `model/History.tla:195`, `model/History.tla:222`, `model/History.tla:259`).
- **End work implemented with an independence qualification:** next-selector oracle, reversed-batch regression and empty-with-eligible regression exist. Timestamp/minted exactness is documented, but EndNext itself only checks msgid continuation; see §3 (`HISTORY-REVIEW-3.md:15`; `model/History.tla:301`; `model/mkhist.py:95`; `DECISIONS.md:471`).
- **Unknown work implemented, but isolation is partial:** selector forms are explicit; LATEST is deliberately restricted to `*`; minted continuation and unknown-answer mutation are checked. There is no direct unknown-selector fixture with otherwise stable replay IDs; see §4 (`HISTORY-REVIEW-3.md:16`; `model/History.tla:117`; `model/mkhist.py:85`; `DECISIONS.md:465`).
- **Identity limitation retained honestly:** content-based recovery and msgid-based dedupe/anchors remain separate; ReplayIdStable remains a range check, not provenance. No new provenance proof was supplied or claimed (`HISTORY-REVIEW-3.md:17`; `model/History.tla:186`, `model/History.tla:234`, `model/History.tla:258`, `model/History.tla:281`).
- **Named tie witness supplied:** W_TieReconnect removes Stable from the budget positive and fails NoLoss. Source/config attribution is now supplied; causal traces, concrete client fixtures and whole-page correspondence are still absent from these artifacts (`HISTORY-REVIEW-3.md:10`, `HISTORY-REVIEW-3.md:23`; `model/mkhist.py:37`, `model/mkhist.py:73`; `model/results-h1.summary:32`).

## 2. Obligations, vacuity and FAIL

- **Reconnect is right within its declared bounds:** recover every initial gap content on every non-FAIL completion, including budget/floor/end/empty/held stops. It does not promise recovery of a subsequently stored live message. Completion and multi-page covers, loss witnesses, and the FAIL/no-exception pair separate success, ordinary loss and refused requests (`model/History.tla:55`, `model/History.tla:259`, `model/History.tla:315`; `model/results-h1.summary:5`, `model/results-h1.summary:17`, `model/results-h1.summary:18`, `model/results-h1.summary:25`).
- **JOIN is right under ExactCount/Contiguous:** recover the newest Limit contents of the first reply's snapshot, from an empty buffer. This is stronger than unconditional protocol compliance: the spec permits fewer messages. HJoin plus its completion cover and W_JoinHoles separate a nonempty success from omission; HJoinFail also explores success and refusal, but lacks its own completion/FAIL covers (`model/History.tla:106`, `model/History.tla:265`, `model/History.tla:324`; `model/mkhist.py:8`, `model/mkhist.py:61`; `model/results-h1.summary:28`; `../formal-spec/specs-src/extensions/chathistory.md:69`).
- **More is right for the pinned stable msgid order:** recover the nearest Limit older contents, not the whole older store. Its cover requires only some older content, but the positive invariant requires the full target set. Holes, timestamp ties and the newest-held anchor mutant all fail that same obligation; two held messages make the anchor mutation meaningful. Timestamp ties are a limitation of timestamp pagination, not proof of an invalid BEFORE reply (`model/History.tla:269`, `model/History.tla:325`; `model/mkhist.py:16`, `model/mkhist.py:67`, `model/mkhist.py:98`; `model/results-h1.summary:53`; `../formal-spec/specs-src/extensions/chathistory.md:83`).
- **No current reachable non-FAIL exemption leak, but the JOIN/more oracle is weaker than the stated rule.** They require `why = "one"`, rather than `why # "fail"`. Today positive budgets allow the first query and every successful page sets "one", so ordinary losses are checked. A future client that erroneously stops with "budget"/"empty"/"floor" would escape both obligations. Strengthen the guard to all non-FAIL completions (and define pre-reply JOIN expectations separately). Also add HMoreFail and mode-specific FAIL covers: MayFail is never enabled for more in this suite (`model/History.tla:204`, `model/History.tla:226`, `model/History.tla:265`, `model/History.tla:269`; `model/mkhist.py:60`).

## 3. End oracle and regressions

**EndNext is independent of EndOK's first-position test, not independent of server eligibility.** Its nonempty branch constructs a fresh next msgid query; its empty branch trusts the stored `el`, and both paths ultimately depend on Elig. It catches EndOK mutations, but cannot independently catch an Elig bug shared by generation and oracle (`model/History.tla:145`, `model/History.tla:153`, `model/History.tla:301`).

**Both requested regressions are real.** HS_EndLast changes only first to last position on a configuration admitting reversed batches; CoverEndReversed reaches that shape. HS_EndEmpty permits an end tag on a prematurely empty page with nonempty eligibility. Each fails EndNext specifically, rather than an unrelated bundled invariant (`model/mkhist.py:76`, `model/mkhist.py:95`; `model/results-h1.summary:33`, `model/results-h1.summary:47`, `model/results-h1.summary:48`).

**D26's exactness note is substantively correct, imprecisely worded.** Minted nonoldest first IDs make next opaque lookup empty; tied timestamps can likewise make strict BEFORE empty despite nonfirst position. EndOK is conservative for both. However, EndOK itself does not decode: SrvAnswer supplies content IDs, and EndTruthful explicitly decodes wire IDs. EndNext always builds a msgid query, even when MsgidAnchor is false; it does not validate timestamp exactness. These are snapshot claims, not guarantees against future store changes (`DECISIONS.md:469`, `DECISIONS.md:471`; `model/History.tla:139`, `model/History.tla:151`, `model/History.tla:304`, `model/History.tla:309`).

## 4. Unknown lookup

UnknownEmpty reads the raw selector against the snapshot order, not decoded content or the generator's eligible set: good isolation of the returned-page condition. HS_NewIdUnknown reaches an unknown continuation, and HS_UnknownLatest keeps minting fixed while changing only unknown lookup to return the store; UnknownEmpty catches that change. Thus the lookup regression is separated from content duplication (`model/History.tla:292`; `model/mkhist.py:88`; `model/results-h1.summary:45`, `model/results-h1.summary:46`).

**Do not overclaim HS_NewIdAnchor's causal evidence.** It checks only NoLoss; minting also changes dedupe and held overlap. A failing-property summary alone does not show the particular unknown/empty/loss chain. Preserve that trace, or add a cover joining unknown query, empty response and missing gap. A direct opaque unknown request with stable replay IDs would remove minting entirely. Empty-on-unknown is D26's chosen behavior; MI's opacity rule alone does not mandate that server response (`model/mkhist.py:79`, `model/mkhist.py:87`; `model/History.tla:187`, `model/History.tla:230`; `DECISIONS.md:466`; `../formal-spec/specs-src/extensions/message-ids.md:41`).

## 5. Smallest replay adapter

Start with a deterministic single-target fake IRC transport plus buffer seeding/snapshot hooks and an outbound-request recorder. Reuse trace-to-wire fixtures for Seance, then Textual-NG and HexDroid; each client needs only its transport/buffer binding. Compare actual selectors, request count, stopping and buffer IDs/content/times, rather than feeding the model's decisions back as expected client behavior. This is proposed work, not an implementation claim: the supplied model and generator contain no client binding (`HISTORY-REVIEW-3.md:23`; `model/History.tla:202`, `model/History.tla:212`; `model/mkhist.py:120`).

Map integer IDs to opaque strings (including distinct minted IDs), contents to fixed bodies, and times to fixed UTC timestamps preserving ties. Use one target `#h` and fresh batch reference `b` per reply. Concrete action fixtures are:

| Model action | Adapter fixture |
|---|---|
| Init | Seed held messages and policy/budget; trigger reconnect, first JOIN, or manual more. Fix server store/order/time choices; no incoming line. (`model/History.tla:101`) |
| CQuery | Assert `CHATHISTORY LATEST #h * L`, or `CHATHISTORY BEFORE #h msgid=<opaque-anchor> L`, or `CHATHISTORY BEFORE #h timestamp=<UTC-anchor-time> L`. Budget exhaustion emits no request. (`model/History.tla:199`, `model/History.tla:202`) |
| SrvAnswer | Queue `:s BATCH +b chathistory #h`, optionally prefixed `@draft/chathistory-end`; then each ordered `@batch=b;msgid=<wire-id>;time=<UTC> :n!u@h PRIVMSG #h :<content>`; finally `:s BATCH -b`. Empty reply has only start/end. (`model/History.tla:143`; `../formal-spec/specs-src/extensions/chathistory.md:166`) |
| SrvFail | Queue `:s FAIL CHATHISTORY MESSAGE_ERROR <LATEST-or-BEFORE> #h :Messages could not be retrieved`, with no history batch. (`model/History.tla:158`; `../formal-spec/specs-src/extensions/chathistory.md:154`) |
| StoreLive | Add live content to fake server store, newest in order; emit no line. (`model/History.tla:165`) |
| RelayLive | Queue `@msgid=<live-id>;time=<UTC> :n!u@h PRIVMSG #h :<live-content>` without `batch`. (`model/History.tla:172`) |
| CRecv | Drain the next queued reply block, FAIL or live line; let the real client parse/merge/stop, then assert state and subsequent output. No extra wire message. (`model/History.tla:212`) |

**Whole-page replay is sound only for the restricted contiguous-block schedules.** It can drive the first catch-up unit replay now. It cannot establish parser/batch conformance: live traffic may occur inside a batch, and clients may process history incrementally. Before claiming replay coverage of real IRC schedules, add line-level fixture interleaving and show that its projected completed-page/live events refine this model, or extend the model if they do not. Test an unbatched duplicate live line between history members and equal-time insertions in particular; batching can change dedupe/merge order. No client-specific correspondence can be established from the allowed files (`model/History.tla:20`, `model/History.tla:191`; `DECISIONS.md:473`; `../formal-spec/specs-src/extensions/batch.md:51`, `../formal-spec/specs-src/extensions/batch.md:55`, `../formal-spec/specs-src/extensions/batch.md:96`).
