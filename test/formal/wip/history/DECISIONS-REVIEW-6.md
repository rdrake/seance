**Verdict: revise before implementing Delivery v2.** D16–D20 are mostly defensible bounded choices, but D19 overstates the code guarantee and D21 leaves consumption holes. Static text/code review only; no TLC. References below use `spec:` for `../formal-spec/specs-src/` and `client:` for `../../client/js/irc/`.

1. **D16: allowed, with restrictions and framing obligations.** Interleaving and nesting are explicitly permitted (`spec:extensions/batch.md:60-63,100-123`). Outermost deferral is allowed client policy, not guaranteed behavior; wire-order folding is the chosen policy (`DECISIONS.md:314-324`). Depth two and one inner batch are restrictions. Require both nested delimiters to name the same parent, membership only while its batch is open, and eventual closure on a surviving connection (`spec:extensions/batch.md:51-63`); “interleave freely” must preserve those constraints and each response's order. Include a **directly labeled chathistory batch**, not just standalone-unlabeled history or a labeled-response wrapper: LR permits an applicable existing type and DESIGN explicitly includes it (`spec:extensions/labeled-response.md:55-58`; `DESIGN.md:16-18`). `history` and `multiline` must be declared abstract names, not literal protocol types: history replies require `chathistory` (`spec:extensions/chathistory.md:71`); the supplied code names `draft/multiline` (`client:handlers/privmsg.ts:383-386`). Multiline assembly semantics are not established by the permitted spec sources.

2. **D17: useful adversarial stress, but its prohibition is not established.** “Answers it twice” is not LR's rule: multiple physical replies inside one logical response are expressly allowed (`DECISIONS.md:328-330`; `spec:extensions/labeled-response.md:53-58`). None of the supplied text explicitly forbids echo plus error for a single target; EM even allows fake echoes for blocked messages (`spec:extensions/echo-message.md:50-52`). Keep adversarial as a conservative modeling choice, rather than claim a proved MUST violation; explicitly restrict the ordinary environment to one settling result. First-wins is client policy. A send-time `firstK` is insufficient if it counts history, otherwise ineligible lines, or a line discarded by close; define it as the first eligible response settlement in the specified processing order (`DECISIONS.md:331-334`).

3. **D18: allowed disconnect; client restriction for cleanup.** Failing remaining copies is supported by `resetPending`, and removal is idempotent (`client:pending.ts:159-176,256-260`). Discarding even already-received buffered replies and making close terminal are chosen client/model policies, not protocol guarantees (`DECISIONS.md:338-346`). Qualify BA's closure obligation: a truncated connection cannot be required to deliver its closing delimiter. An open batch at disconnect must be a legal close trace, rather than D13's missing-closure mutant (`DECISIONS.md:232-233`; `spec:extensions/batch.md:54`). These two decisions currently need reconciliation.

4. **D19: correct conditional guard; incorrect universal heading.** The handler calls `settleEcho` exactly when `self && !client.replaying`; replay routing also uses that flag (`client:handlers/privmsg.ts:85,141-146,299-301`). This verifies suppression **while the flag is true**, not that every historical line sets it. The allowed reads do not include the code that sets the flag or assembles batches, so nested replay integration and the cited historical revision/#277 remain unverified (`DECISIONS.md:350-357`). History may include one's outgoing messages, including messages originally sent on this connection; “not an echo of anything sent on this connection” is too strong (`spec:extensions/chathistory.md:65,125-128`). It is replay, not a new delivery acknowledgment.

   **Yes, history-like lines can reach settlement.** Automatic history batching is a SHOULD, unlike successful negotiated CHATHISTORY replies' MUST (`spec:batches/chathistory.md:22-27`; `spec:extensions/chathistory.md:71`). An unbatched replay with our current nick, a resolvable target, ordinary text and `client.replaying == false` reaches `settleEcho`; matching text/kind/channel can clear a pending copy (`client:handlers/privmsg.ts:85,299-301`; `client:pending.ts:210-228`). Neither old time nor batch type is tested there. Likewise an assembled `draft/multiline` message delivered through this handler with the flag false can settle; multiline alone does not imply history. With the flag true, it cannot. Do not claim how the dispatcher sets that flag from these files. Rename the property to recognized-history suppression and either exercise unrecognized replay as an allowed source of confusion or explicitly exclude it. BA permits unknown-type processing one line at a time (`spec:extensions/batch.md:78-81`).

5. **D20: order/NOTICE/modified echoes are allowed; bounds are restrictions.** LR labels only the self echo and supplies no relative delivery order, so delivered-copy-first is valid (`spec:extensions/labeled-response.md:60,87-92`). NOTICE echoing is a MUST when negotiated; modifications are allowed, but returning the final version is a MUST, with the fake-echo exception (`spec:extensions/echo-message.md:21-35,50-52`). Omitting TAGMSG despite message-tags being enabled is another explicit scope restriction. Choosing only modified text that matches no copy omits the allowed collision case: altered text can equal another pending copy and unlabeled fallback can settle it (`DECISIONS.md:368-370`; `client:pending.ts:215-216`).

   `SameKind` needs scope: fallback checks kind, but label matching checks **only label**, so this is not an unconditional Seance safeguard (`DECISIONS.md:365-367`; `client:pending.ts:203-216`). Error/ACK/close settlements have no echo kind; exclude them from that property. Also document two existing code/model differences: an unusable but present label falls through to content matching, and without labeled-response the oldest same-kind/channel copy can settle even with different text (`client:pending.ts:208-223`; compare `DECISIONS.md:276-277`). The latter is outside the negotiated-capability restriction; the former can matter even with fresh labels after timeout. Finally, “one late reply over the whole run” is stricter than DESIGN's “one ... in flight,” not merely matching its bounds (`DECISIONS.md:371`; `DESIGN.md:54`).

6. **D21: catches standalone ACK/4xx ignoring only when those exact cases are reachable and checked; insufficient as stated.** Immediate consumption excludes every batch member, leaving an immediate client free to ignore batched ACK/4xx (`DECISIONS.md:378-381`). Extend it to eligible non-history members using the effective inherited label when `Deferred` is off. Deferred consumption must use the first eligible settling line through the entire nested tree, exclude replay, and test pending state at outer close. A directly labeled chathistory batch must not acquire a settlement obligation merely because its replay resembles an echo.

   Require the **specific** outcome and recorded owner/cause in that same step: echo → confirmed, ACK → accepted, FAIL/4xx → failed; record causes independently from handler output. “Settled” alone allows the wrong result; DESIGN's one-way OutcomeMatchesCause does not require response consumption (`DESIGN.md:142-154`). Require separate standalone, immediate-batched and deferred-batched ACK and 4xx traces, with the copy pending at consumption, plus separate ignore-ACK and ignore-4xx mutants. ACK needs `Lossy` under D15, so a Lossy-off suite cannot test it (`DECISIONS.md:274`). Keep 4xx distinct from abstract FAIL to expose numeric dispatch omissions, already identified in `MODEL-REVIEW-2.md:9,17,44`. With those obligations and reachability checks, a later timeout cannot hide either omission.
