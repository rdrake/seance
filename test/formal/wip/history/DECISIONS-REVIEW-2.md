## 1. First-review findings still inadequately answered

The remaining finding numbers are **1.2, 1.4, 2.2, 2.7, 2.9, 3.1, 3.3, 3.5 and 4.4**, in the following respects. The other findings have adequate answers within the newly explicit restrictions.

1.1 **Review 1: 1.2 and 1.4 — inventory leftovers.** EM-4 still presents inherited prose as a literal MUST despite the inventory's stated convention (RULES.md:24–25, 66; EM:34–35). The new CH:39 row still omits the server's SHOULD NOT enforce all related capabilities; calling the row descriptive does not inventory that requirement (RULES.md:163; CH:39). ST's permissive client parsing is MAY, absent from that row's level list (RULES.md:170; ST:42). These are editorial corrections, not modelling blockers under D11.

1.2 **Review 1: 2.2 — label lifetime.** D2 now scopes by request/use, but ends its checking window at timeout or complete response. LR:53 does not permit a second labeled logical response after either event. With fresh labels, count logical responses over the request's entire trace, including late traffic; distinguish this from whether the client still has a pending entry (DECISIONS.md:50–52, 195–200; LR:53, 64). Otherwise the duplicate-label mutant can escape detection simply by arriving after completion (DECISIONS.md:56).

1.3 **Review 1: 2.7, 3.1 and 3.3 — ordering assumptions.** The old-anchor qualification and concrete reorder witness are fixed, but the assertion that consistency, selection and budget suffice is still too strong; Order's operational merge is also insufficient. See 3.1–3.2 below (DECISIONS.md:124–145; DESIGN.md:63–70, 88–97).

1.4 **Review 1: 2.9 — AFTER remains contradictory.** D9 says the model has only backward paging and excludes AFTER exhaustion, while DESIGN explicitly gives the server AFTER and D10 defines its selection. Either exclude AFTER consistently or define its forward end-tag semantics (DECISIONS.md:160–166, 170–173; DESIGN.md:29–34; CH:89, 136).

1.5 **Review 1: 3.5 and 4.4 — remaining witness/budget gaps.** The enlarged history bounds fix the original capacity problem, but do not define a failing fuzz witness, Delivery bounds, or precisely when a message budget is tested. See 2.5 and 3.3–3.4 (DESIGN.md:42–50; DECISIONS.md:219–228).

## 2. D10–D14 and switch classifications

2.1 **D10: plausible selected policy, overstated permission.** Exact, nearest contiguous pages are a useful **restriction/allowed policy**, not a text guarantee: CH:83 and CH:89 specify a side, while CH:95 explicitly specifies most recent. CH:69 permits count deviations due to implementation constraints; it does not expressly license arbitrary membership holes merely because the count is relaxed. Classify arbitrary subsets as an adversarial or explicitly uncertain interpretation, rather than asserting CH:69 establishes that permission. Separate selection from cardinality instead of using `ExactPages` to change both (DECISIONS.md:64–70, 170–177; CH:69, 83, 89, 95, 128). Also cap actual cardinality by eligible-set size (DECISIONS.md:65–67).

2.2 **Snapshot and retention: supported restrictions.** A query-execution snapshot and no expiry are explicit modelling choices, narrower than all possible server behaviour, not guarantees. Label both as restrictions; D6 already acknowledges the snapshot abstraction (DECISIONS.md:102–105, 179–180; CH:32). A pre-snapshot message must still satisfy selector eligibility, as D3 says (DECISIONS.md:68–70).

2.3 **D11 and D12: adequate restrictions/client policies.** Requiring IDs, times, capabilities and both reference types is correctly narrower than the text; fresh labels and ignoring late responses after timeout are valid client choices, not protocol guarantees (DECISIONS.md:184–200; MI:31; ST:41–42; CH:39, 51–56; LR:64). Label D12 explicitly as a restriction too. The assertion about Seance's actual allocator cannot be independently verified within this review's permitted inputs (DECISIONS.md:195).

2.4 **D13: correct closure rule, assumed progress.** Mandatory closure and optional deferred processing are supported (DECISIONS.md:204–206; BA:54–55, 63). Weak fairness is an environment/client **restriction**, not timing guaranteed by the specs. Define fair timeout/processing per pending request, and make every terminal outcome absorbing, including a confirmed or failed request whose deferred batch processing subsequently finishes (DECISIONS.md:207–212; DESIGN.md:101–106). D12 explicitly makes only timeout absorbing (DECISIONS.md:198–200).

2.5 **D14: useful policies, specify the guard.** Pages versus retrieved messages is now correctly distinguished (DECISIONS.md:216–226). For fidelity to the spec, `messages(m)` checks before issuing a query and counts the whole returned page; it may overshoot m. It must not truncate the page or refuse a page merely because it could exceed the remaining budget (CH:196–205). Label both budgets client restrictions, and define that guard before implementation (DECISIONS.md:219–221).

2.6 **Other switches.** `Lossy` is correctly adversarial for the selected feasible-response environment; immediate/deferred processing and optional truthful end emission are allowed (DECISIONS.md:26–35, 53–55, 163–165; BA:55; CH:136). Neither exact pages, stable reconnect order, ascending time nor batch/order agreement is guaranteed: CH:69 permits count deviations and CH:126–128 uses SHOULD. Explicitly classify those selections and resolve whether `TimeOrdered` controls batch order, connection order, or both: D7 requires time agreement even with stability off, then separately permits time disorder (DECISIONS.md:131–135; RULES.md:99–102).

## 3. Properties and reachable witnesses

3.1 **NoLoss still needs a safe timestamp stop.** Require the first-version monotonic-time environment and a connection order compatible with it, or an explicit condition ensuring no unseen gap message lies behind a below-floor page. Store-time monotonicity alone does not constrain an arbitrarily reordered connection. Within the bounds, hold A at time 1 then H at time 3, store gap G at time 3, and reconnect with order G,H,A. With `TimeOrdered` off, LATEST 1 returns A; the spec loop stops below floor 3 and misses G despite exact selection, batch/order agreement, IDs, no errors and an ample two-page budget. An extra live message can occur after this query. This uses DESIGN.md:43–47 and exposes the missing condition in DESIGN.md:63–70 and DECISIONS.md:144 (CH:204–208). D8's chosen environment should be an explicit property condition, with its interaction with D7 settled (DECISIONS.md:131–150).

3.2 **Order's condition is partly circular and its implementation does not follow.** “Merges by that order” would suffice, but “by time, with ties by arrival in the batch” does not establish it across pages, held messages or live lines (DESIGN.md:88–97; CH:128). Example within the bounds: held H, gap G,B, all time 1, and live L at time 3; connection order H,G,B,L. Exact pages of two return B,L then H,G. Arrival-based tie insertion can leave H,B,G,L. Specify page-relative insertion and how old/live equal-time messages obtain current-connection order, or state access to server ranks as an explicit oracle abstraction (DESIGN.md:43–47; DECISIONS.md:80–86, 99–112). Turning `TimeOrdered` off does not itself produce the claimed out-of-connection-order batch witness: an unsorted-by-time batch may still agree perfectly with connection order. Use the separate batch/order-agreement switch (DESIGN.md:96; RULES.md:102).

3.3 **Main history witnesses fit.** The four-message D7 reorder, timestamp tie exclusion, live/page duplicate, and three-gap/two-one-message-page budget failure fit the revised bounds (DECISIONS.md:88–90, 107–109, 137–141; DESIGN.md:43–48, 72–86). For the short-page failure choose an empty page while eligible gap messages remain; a merely nonempty short contiguous page need not lose anything in the spec loop (CH:201–208; DESIGN.md:73). Nonempty-gap successful completion is also possible with one held and one gap message, a sufficient page and a truthful end tag (DESIGN.md:45–47, 58–69; CH:136). However, the fuzz witness is not defined: with monotonic store times, no backward skew and Fuzz=0, reducing fuzz supplies no loss mechanism. Reaching both stop and continue tests is branch coverage, not a failing fuzz witness (DESIGN.md:49–50; DECISIONS.md:149–156).

3.4 **PendingResolves witness is conceptually valid, not yet bounded.** A dropped request with timeout disabled can stutter pending forever; the same request resolves under a fairly enabled timeout (DESIGN.md:101–109; DECISIONS.md:209–212). DESIGN's bounds specify history messages, queries and reconnects, but no finite Delivery request/label/batch domains. Bound requests and allocate distinct labels from a finite pool without recycling; specify nested-batch depth and delayed-response capacity (DESIGN.md:36–50; DECISIONS.md:195–200; RULES.md:40). NoDup's new condition and content-identity mutant are sound (DESIGN.md:78–86; MI:39; CH:126).
