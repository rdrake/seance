# Decisions review 1

**Verdict: revise before modelling.** The timestamp reading in D5 and live-message placement in D6 are defensible, but the rules inventory misstates a limit, omits relevant requirements, and the proposed properties and witnesses do not yet justify their claims (findings 1.1–3.5). D7 correctly reads the full-support gap-fill loop but overgeneralises to other pseudocode (2.7).

Source qualification: this review read only the three requested review inputs and the eight permitted spec files. The requested commit `9ff58d1` could not be resolved by `git -C ../formal-spec show`; Git instead identifies the enclosing Seance checkout. Consequently this is a review of the supplied spec text, **not a verified review of that commit**. References below use RULES.md's prefixes (RULES.md:11–22); CH, BA, LR, EM, MI, ST and MT mean `../formal-spec/specs-src/extensions/<name>.md`, and CB means `../formal-spec/specs-src/batches/chathistory.md`.

## 1. RULES.md

1.1 **Wrong meaning of zero.** CH-3 says `CHATHISTORY=0` means “none” (RULES.md:86). It means the client SHOULD assume **no maximum** (CH:49). Separate the server's MUST advertise from the client's SHOULD interpret zero.

1.2 **Normative levels are inflated or conflated.** CH-10/11's MUST concerns supplying exactly one selector; “up to limit ... before/after” is descriptive prose. Likewise CH-12/13's MUST concerns selector exclusivity, not all the prose collected in those rows (RULES.md:93–96; CH:83,89,95,103). Preserve the semantic descriptions, but distinguish their level. CH-4 omits the SHOULD on assuming both reference types when the token is absent (RULES.md:87; CH:56). EM-4 inherits echo rules through plain prose, rather than containing a literal MUST (RULES.md:24–25,66; EM:34–35).

1.3 **Important omitted ordering requirement.** CH-19 leaves out that the consistent order SHOULD coincide with response-batch order (RULES.md:102; CH:128). Ascending timestamp order is a separate SHOULD (CH:126). This omission directly affects paging anchors and the Order property (DESIGN.md:55,57; CH:204,208).

1.4 **Other missing requirements, even if abstracted out.** Inventory these explicitly with an out-of-scope marker where appropriate: draft/unprefixed capability names and batch naming (CH:27–29); not enforcing all related capabilities (CH:39); optional event-playback and its additional-line SHOULD (CH:43,73); secure history identification SHOULD (CH:245); batch capability naming, reference alphabet, vendor type prefixes and opaque type names (BA:29,46,67–72); opaque label values (LR:64); echo capability naming (EM:19); MAY attach IDs, forbidden ID bytes, and SHOULD offer echo (MI:31,37,45); timestamp syntax, optional timestamps, permissive client parsing and SHOULD offer echo (ST:31–44). The existing inventory records comparable preconditions and syntax exclusions, so silently omitting these is inconsistent with its “every normative sentence in scope” claim (RULES.md:5,33–42,54,73,116–118).

1.5 **Message-tags is almost entirely absent.** MT-1 alone does not cover the tag framework used for labels, IDs and batch references (RULES.md:118; LR:33; BA:51). Relevant missing rules include unique keys and duplicate-key handling (MT:53), opaque keys and acceptance of invalid key names (MT:55,154), UTF8 and empty/missing equivalence (MT:57–59), escaping (MT:76–79), full-format support (MT:83,100), and removing unprefixed client tags before relay (MT:257–262). If wire handling is in scope, also inventory tag ordering, naming, size/rejection and TAGMSG requirements (MT:120–127,140–150,165,185–186,196–209), and CLIENTTAGDENY rules (MT:215,221,225,231). Otherwise explicitly exclude those layers; one relay row does not establish a complete inventory (RULES.md:5,118).

1.6 **Wrong or incomplete citations and paraphrases.** CB-1's requirement is CB:17–20, not 14–17; CB-2's timestamp MUST is CB:25–27, not 19–23 (RULES.md:114–115). CH-23/D6's ignore-live advice is CH:214, not CH:221–224 (RULES.md:106; DECISIONS.md:83–85). BA-9's unbatched interleaving example is BA:93–98; BA:100–112 demonstrates interleaved batches (RULES.md:41). CH-5 omits the required selector formats (RULES.md:88; CH:67). MI-4's “accept shared ids” does not require deduplication, and MI-6 does not require ordering by time (RULES.md:76,78; MI:39,74–76). Those are client choices.

## 2. D1–D9

2.1 **D1: supported outcomes, excessively broad permission.** The four outcomes are genuinely illustrated, but for asynchronous remote commands whose responses become infeasible; LR does not grant arbitrary loss of every otherwise feasible response (DECISIONS.md:10–21; LR:53,76–83). Make the feasibility condition explicit, or identify Lossy as an adversarial environment beyond that guarantee. “Only” timeout resolves in Lossy mode is false: a labeled ACK, a closed partial response, or an ordinary labeled response may still arrive (DECISIONS.md:23–25; LR:78–81). Early response termination means incomplete content, not permission to omit BATCH closure (BA:54; LR:80).

2.2 **D2: batch correlation supported; processing timing and label lifetime overconstrained.** A labeled batch is one logical response, and additionally labeling its echo violates that rule (DECISIONS.md:29–40; LR:53–58). But waiting until batch end before resolving a pending echo is a client policy, not required by BA-5: immediate processing is allowed (BA:54–55,63). More seriously, “per label ... ever” forbids reuse even after a complete response; scope the invariant per request/use of a label (DECISIONS.md:38; LR:64). Model both processing policies if claiming all allowed client behaviours (RULES.md:38).

2.3 **D3: bounded abstraction acceptable, eligibility remains mandatory.** PRIVMSG-only/no-context is an explicit restriction (DECISIONS.md:48–49); it does not exercise NOTICE or context requirements (CH:73,132). “Any count ... to store size” must still select eligible messages for the query, excluding its anchor (DECISIONS.md:50–53; CH:83,89,95). Relaxing count cannot simulate admitting forbidden event lines or moving context into the counted set (CH:73,132). Also distinguish page cardinality from which eligible messages are selected: exact count alone is insufficient to define contiguous pages (CH:69,95,128).

2.4 **D4: acceptable exclusion, misleading open question.** BETWEEN is explicitly out of the current model (DECISIONS.md:55–58; DESIGN.md:33–34). Its counting direction is already settled: from the first selector toward the second, excluding both, in either temporal direction (CH:111). No additional direction reading is needed unless specifying behaviour not covered there.

2.5 **D5: strict timestamp exclusion supported; representation and expiry need care.** BEFORE excludes all messages at the selected timestamp, whereas a msgid can split equal-time messages using the consistent order (DECISIONS.md:62–75; CH:83,128). The proposed tie-loss witness is appropriate for a timestamp-paging client, but the full-support pseudocode pages by msgid (CH:208). Do not represent an opaque msgid solely as a permanent position: D7 permits positions to change, while IDs remain identities (DECISIONS.md:70–72,110–112; MI:41; CH:126). Unknown/expired-ID handling really is unspecified; empty-or-FAIL is a chosen subset, not all text-permitted handling, and stopping on either is client policy (DECISIONS.md:77–79; CH:141–160).

2.6 **D6: placement supported, page membership must be constrained.** Untagged live delivery before, during or after a history batch is allowed (DECISIONS.md:88–89; BA:93–98; CH:214). Inclusion must follow query eligibility, count policy and the chosen query snapshot, rather than independent nondeterminism (DECISIONS.md:90; CH:69,83,89,95). The text does not mandate a snapshot instant, so explicitly identify that abstraction. A duplicate witness needs a live message actually included in the page; a live-only message cannot demonstrate dedupe (DECISIONS.md:92; CH:214). Interleaving also defeats any assumption that batch sorting alone sorts the whole buffer (DESIGN.md:57; CH:128).

2.7 **D7: correct about one loop, incorrect as a general claim about old IDs.** In CH:192–208, every BEFORE anchor does come from a current-connection page, and the old session contributes a timestamp. However CH:218–220 explicitly uses a previous-session msgid as a BETWEEN anchor. Therefore “never an anchor in the spec's algorithm” needs qualification; single-connection order consistency does not itself prohibit looking up older message identities (DECISIONS.md:98–107; CH:128,218–224).

The overlap-stop risk is real but needs a concrete witness and a defined held set. Within four messages, let H1,H2 be held, G,B arrive during the gap, and all four have the same time. Old receipt order H1,H2,G,B becomes G,H1,H2,B on reconnect; LATEST 2 returns H2,B. Stopping on held H2 misses G. Stable order instead returns G,B first. This exercises DECISIONS.md:110–117 within DESIGN.md:39–43, assuming the second timestamp value is available but need not occur in every trace. Conversely, a spec-loop success claim still needs batch/order agreement and sufficient traversal budget (CH:128,196–208). The “only reorder” assertion is too strong: receipt-time tagging is a SHOULD, not a guarantee of monotonic store order (DECISIONS.md:111–112; CH:126,128).

2.8 **D8: valid explicit restriction; proposed skew theorem is unsupported.** One server with monotonic times is a useful selected environment, not guaranteed merely by using one server (DECISIONS.md:124–129; CH:126,128,239). Bounding each predecessor-to-successor timestamp drop by Skew does not bound cumulative backwards skew: several drops can exceed Fuzz. Replace the proposed `Skew <= Fuzz` condition with a bound on total displacement relevant to the stopping floor, and account for batch order and traversal budget (CH:193,196,204–208).

2.9 **D9: correct end-tag meaning for backward paging; switch is narrower than allowed.** A truthful end tag predicts an empty next page (CH:136). “Older” fits BEFORE/LATEST backward pagination but cannot define AFTER or TARGETS exhaustion generally (DECISIONS.md:137–139; DESIGN.md:33; CH:89,119). SHOULD permits selective omission; always-correct versus never-sent excludes partial emission (CH:136). Model optional truthful emission per response if all allowed behaviour is intended. A false-tag mutant is appropriate (DECISIONS.md:139–140; CH:136).

## 3. Properties and witnesses in DESIGN.md

3.1 **NoLoss needs more conditions.** Exact count, consistency and “gap fits” do not alone ensure the gap is traversed: specify contiguous page selection, batch/order agreement, msgid availability, truthful end tags, selector choice and no truncating timeout/error/retention event (DESIGN.md:55; DECISIONS.md:50–51,77–79; CH:32,69,95,126–128,136,154–160,204–208). The budget must cover all fetched messages, including overlap/fuzz and live messages, not just the missed-message count (CH:193,196–208; DESIGN.md:42–43). Reordering across reconnects is a witness against the overlap stop, not automatically against the spec loop (DECISIONS.md:113–117).

3.2 **NoDup's condition and witness do not match its statement.** “No msgid twice” requires client dedupe; ID reuse alone does not provide it (DESIGN.md:56; MI:39,76; CH:190,205). Minting new IDs for replay creates duplicate content with different IDs and therefore does not falsify that invariant. It also violates CHATHISTORY's original-ID MUST, irrespective of MI's generic retransmission SHOULD (CH:126). Use a non-deduping client for an ID-duplicate witness, or define content identity separately and classify new-ID replay as a nonconforming-server mutant.

3.3 **Order needs a definition and additional conditions.** Ascending timestamps do not determine equal-time order, and a sorted batch says nothing about merging delayed live messages into the buffer (DESIGN.md:57; CH:126,128; DECISIONS.md:88–91). Require agreement with the chosen total order and a client merge policy that preserves it; clarify whether the property is continuous or only checked after catch-up completes.

3.4 **PendingResolves needs client progress, not just labels and echo.** Require eventual response processing or a fairly executing finite timeout, and terminal-state handling of late responses (DESIGN.md:58; DECISIONS.md:23–25; LR:79,81). A dropped response with an active timeout demonstrates success, not failure with the switch off. Also define “confirmed, failed or timed out, exactly once” as exactly one terminal outcome, rather than exactly one confirmation: blocked messages may still receive fake echoes (EM:50–52).

3.5 **Some witnesses may be unreachable at Tiny bounds.** With at most four total stored messages, exact pages of two and two pages cover the entire store; an exact-page gap-over-cap witness is impossible unless the live message is additional to the four, or the bounds/budget change (DESIGN.md:39–43,55). Specify which. Two timestamp values do not guarantee a useful floor-minus-fuzz boundary: fix their spacing and Fuzz to exercise both stopping and continued paging (DESIGN.md:39; DECISIONS.md:73–75,114; CH:193,206). Avoid a vacuous “after catch-up” implication by requiring reachable completion with a nonempty gap and a separate termination/progress check (DESIGN.md:55; CH:196–208).

## 4. Missing decisions

4.1 **Page selection and snapshots.** Decide contiguous nearest-page selection versus arbitrary eligible subsets, when a query sees a live insertion, and whether history can expire during paging; these change NoLoss even with exact cardinality (DECISIONS.md:50–51,88–90; CH:32,69,83,95,128).

4.2 **Identity availability and client lookup.** Decide whether missing IDs/timestamps/reference-type support are explicitly excluded or modelled, and how stable message identity maps to each connection's order. Full message-tags support does not guarantee a bouncer supplies IDs, and timestamp fallback is explicitly contemplated (CH:39,51–56; MI:31; DECISIONS.md:70–72).

4.3 **Label reuse after timeout and late responses.** Decide fresh-label allocation versus reuse and how a delayed old response is prevented from resolving a newer request. Timeout is not receipt of a complete response, and late unlabeled responses are explicitly possible (LR:64,81; DECISIONS.md:23–25,38).

4.4 **Processing and termination policies.** Settle early versus end-of-batch processing, partial response completion versus missing batch closure, and fairness for reply delivery/timeouts; otherwise Delivery's safety and liveness claims are underspecified (BA:54–55,63; LR:80; DESIGN.md:58; DECISIONS.md:33–34). Also distinguish the spec's retrieved-message sanity limit from the chosen scaled page cap; they are different bounds, not literal translations (CH:195–203; DESIGN.md:43; DECISIONS.md:114).
