# Eighth review: drop-point trace constraint

**Verdict: the drop check is not a faithful encoding of backend loss, and a `server` frontier at k+1 is not evidence of a server violation.** It imposes an immediate internal-state deadline in a different clock from the recording, without recording either backend loss or server detection. It does require an observed DEL in the important non-vacuous case, but does not establish the claimed general guarantee (`conformance/check.py:40-45,66-81`).

1. **What it actually forces; vacuity.** `ti` counts server *sends* (`NewOut`), not client reads (`conformance/check.py:68-71`; `model/SpecHandshake.tla:13-18,532`). The implication requires sasl absent in every successor with `ti > k`, including successors of steps that emit nothing. It does not require availability through k, an environment transition at k, or any transition at all when the recording ends there.

   If sasl starts offered and output passes k, only `EnvChange` can remove it; that action appends a real `DEL {sasl}`, which must match the recording (`model/SpecHandshake.tla:373-392`; `conformance/check.py:69`). Thus an advertised-sasl trace continuing beyond k cannot simply hide an unrecorded DEL. However, a matching DEL **before or at k** suffices: no guard ties that withdrawal to the drop. If sasl starts absent, the consequent already holds; if the run ends with `ti <= k`, the antecedent never holds, and `Settled` does not require `EnvChange` (`conformance/check.py:64,77-81,95`). `MaxEnv >= 1` is permission, not an obligation.

   An LS in flight does not create a loophole for silently changing `offered`: `SrvSend` only transports previously sent output, while an LS continuation uses the current offered set (`model/SpecHandshake.tla:229-242`). It does expose the clock mismatch: the model can have sent LS lines that the recorder has not read. Nor is `srv.offered` the client's knowledge: LS reception accumulates `cli.avail`, and only DEL reception removes it (`model/SpecHandshake.tla:411-415,435-444`; `DECISIONS.md:126-128`). Internal absence does not mean the client has been notified.

2. **Boundary and permitted delay.** A sasl DEL at k+1 is allowed by the predicate: the DEL step both increments `ti` and removes sasl in `srv'`. There is no intrinsic off-by-one rejection of that line. With sasl initially offered and no earlier withdrawal, DEL only at k+2 or later is rejected as soon as the intervening line is emitted, regardless of whether that delay is legitimate. A prior DEL can satisfy the deadline, but cannot explain a second late sasl DEL without a NEW; a NEW restoring sasl after k is itself forbidden (`model/SpecHandshake.tla:376-390`).

   The recorded anchor is weaker than “backend went down after line k.” The drop marker follows the blocking drop call; no reads are processed during it, and even lines already in the socket or `c.buf` can be processed afterward (`conformance/drive.py:185-188,232-250,278-281`). `dropAt` counts reduced, LS-collapsed observations, not all wire lines (`conformance/drive.py:342-368`). It measures client event processing, not server send time or detection time.

   CN:450-457 defines notification and cancellation boundaries; cap-notify enables notification but sets no numerical line or time deadline (`specs-src/extensions/capability-negotiation.md:450-457,474-479`). S2 also calls for availability notifications (`specs-src/extensions/sasl-3.2.md:53-58`). Neither licenses choosing a particular finite slack such as one or two lines. Allow transport and detection delay; any finite test timeout is an explicit harness assumption, not a protocol-derived deadline.

3. **Real backend: separate loss, detection, withdrawal.** On the stated request-driven detection mechanism, an unrelated k+1 line says nothing about whether the server has learned of backend loss. A failed request can trigger detection and then notification; the current predicate can forbid even that failure reply before DEL. The model does not implement the physical loss: `drive.py` still records `svcOk = True`, and `env` is fixed; `EnvChange` changes `authUp/offered` and sends DEL, while request handling also consults the distinct `env.svcOk` (`conformance/drive.py:371-374`; `model/SpecHandshake.tla:84,166-179,373-392`).

   A fair encoding needs a recorded external down event ordered among client **read/send events**, distinct server detection, and a notification obligation after detection. Permit output already sent or buffered and unrelated output while detection is pending. Instrument detection or provoke and identify a failed backend request; without such evidence, retain detection timing as nondeterministic and label the result inconclusive about prompt withdrawal. Once detected, require eventual appropriate notification, with any experimental deadline stated separately. For `beforeConnect`, initialize backend availability down rather than pretending it changes after LS: currently `dropAt=0` plus sasl in the inferred initial offered set prevents the first LS, while `EnvChange` cannot run until LS has been handled (`conformance/drive.py:267-272,371-374`; `model/SpecHandshake.tla:134-143,374`). `CmdServices.drop()` also ignores command exit status, so the marker does not even prove a successful stop (`conformance/drive.py:185-188`).

4. **Other trust limits.**

   - **Frontier attribution is heuristic, not a failed-action proof.** It chooses one state by `(ti+cj, rd)`, potentially preferring more client sends over more observed output, discards tied alternatives, then compares the next client's read requirement to **ti**, not **rd**. It never checks which action is actually enabled. “Client” can mean merely that lines were sent but remain unread; “server” can reflect a client or harness restriction. Even “settle” can mean only the `nread` target was not reached. Return all maximal alternatives with `rd` and actual blocking conditions; report a prefix mismatch separately from blame (`conformance/check.py:123-142`).

   - **`nread` is useful but only an endpoint constraint.** The update correctly counts `CRecv`, including its atomic AUTHDATA response, and client sends are pinned to `rd'` (`conformance/check.py:71-81`; `model/SpecHandshake.tla:445-448,461-469`). However, there is no cap `rd <= nread`; exploration/frontier selection can over-read an intended unread suffix. A trace with `rd < nread` and all sends reproduced is also labelled “settle.” Validate `0 <= nread <= Len(Obs)` and client read anchors against it. `Settled` checks transport delivery, not consumption: an unread suffix can remain in `s2c`. That is reasonable for a stopped reader, but does not prove the client handled those lines (`conformance/check.py:77-81`; `model/SpecHandshake.tla:229-233`).

   - **Match means bounded existential compatibility.** `TSpec` omits fairness and searches for a reachable quiescent endpoint via invariant violation; it is not a temporal conformance proof. In particular `Settled` omits environment changes, so cannot establish eventual withdrawal. Clean traces get no drop predicate and no new minimum environment allowance, but retain these limitations (`conformance/check.py:44-45,75-105,159-163`; `model/SpecHandshake.tla:564-575`). Initial offered caps are inferred from the whole LS union, and LS collapsing assumes no client event inside that run; these abstractions need checking before generalizing beyond these schedules (`conformance/drive.py:76-98,356-374`). A per-trace match under either Reauth setting also does not establish one consistent server setting across runs, as the checker itself notes (`conformance/check.py:178-192`).
